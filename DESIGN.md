# Tern × GitButler: design note

Plugin id `gitbutler`. See the README prerequisites for the currently tested Tern and GitButler CLI versions.

Runtime files live in `plugin/`, the linked package; `plugin/AGENTS.md` owns the file map. `.git` stays at the repo root because Tern reloads plugins on any change inside the package.

## Is this folder GitButler-managed?

One function, `gb.root(path)` in `gb.luau`, required by both halves:

1. Walk up from `path` to the first `.git`. A `.git` file (a linked worktree) is followed through `gitdir:`, then `commondir`.
2. Managed when `<gitdir>/HEAD` is `ref: refs/heads/gitbutler/…` (`workspace`, or `edit` during `but resolve`) **and** `<commondir>/gitbutler/` exists.
3. Return the worktree root, or `nil`.

The check only stats and reads files, with no process, so it is cheap enough for window handlers (50 ms budget) and fits inside the 2 s host budget. It turns false after `but teardown`, because HEAD leaves `gitbutler/`. Every surface calls it.

It answers "must raw git stay out?", not "does `but` know this project?". `Atlas/Iris`, `GAT/Card2` and `Websites/SIGsite` are on `gitbutler/workspace` but missing from but's project list, so `but status --json` returns `{"error":"setup_required"}`. For those repos the segment reads `GitButler: run but setup`, and the block shows the error.

## Surfaces

| Need | Tern surface | Half |
| --- | --- | --- |
| Status segment (applied branches, unpushed commits) | `tern.chrome.status` reads a cache. `focus`/`cwd`/`command_finished` events and a 30 s timer refresh it with an async `but status --json`. `command_finished` re-probes the focused cwd at once, then every other pane cwd in `tern.timer(0)` chunks of about 10 ms (a newer command supersedes an older sweep), overwriting cache entries in place and refreshing chrome when one changed, then drops entries no pane uses. So a segment drops after `but teardown` even in an unfocused pane, a child cwd picks up `but setup`, other repos keep their segment, and the handler stays inside the 50 ms window budget | window |
| Workspace block (lanes, uncommitted files, assignments, actions) | `[[blocks]] workspace`. Polls with `tern.process.run` (review-queue pattern), `r` refreshes. Views share the rows, action cursor and viewport anchor; see the README's [view guide](README.md#next-steps) for their appearance and controls. The choice is stored in `tern.kv` (`view`) for new blocks. Every view draws `el` nodes styled by `styles.css` (manifest `styles`, scoped to `[data-surface="plugin.gitbutler.workspace"]`; Tern CSS has no `ch` unit, so widths use `var(--sf-cw)`). Lists are windowed because `main` never scrolls. CSS `flex-wrap` controls side-by-side versus stacked layout; `cx.cols` guides height budgets because the block's reported size can lag its pane | host |
| Board view (GitButler desktop parity) | A toolbar (Commit, Absorb, New branch, Pull, Undo, Redo, Oplog, Discard…), the Uncommitted column with a checkbox per file (the same marks as space), one column per stack, and a New branch column. Block nodes get `click`, `dblclick` and a right-click `menu` but no drag events, so the GUI's drag is select-then-drop: the selected card, or the checked files, is what moves, and each card that can take it shows a drop button (`drop=<op>:<target key>`): files → "Commit here" on a branch, "Amend" on a commit, "Commit to a new branch"; a commit → "Squash"/"Above" on another commit, "Move here" on a branch, "Uncommit" on Uncommitted, "Move to a new branch"; a committed file → "Move in" on another commit, plus the same branch, Uncommitted and new-branch targets. A selected commit opens to its files. Right-click lists a card's actions; Tern labels menu items with their action id, so ids are plain labels (`MENU`) and the row comes from the event's node id (`….L<lane>.<key>`) | host |
| Top bar: view tabs and sync chips | First node of `main` in every view. Tabs (`view=<name>`, keys `1`-`5`, `v` cycles) swap the view in the same block. Chips use GitButler's words: `N upstream commits` (the desktop header) or `Up to date` (`but pull`), both `do=f` (pull, which re-checks the target); `N unpushed branches` / `Nothing to push` and `N diverged` count `branchStatus`; `Conflicted` when a commit is; the running command's label. One row when tabs and chips fit `cx.cols`, else chips above tabs; `list_px` reserves `TOP` per row. Branch badges use the desktop app's labels (`gb.STATUS_TEXT`: Unpushed branch, Some unpushed, Nothing to push, Integrated; Diverged from its lite app) | host |
| File/commit diff view | In the workspace block: ⏎ or a double-click sets `state.diff` (bound to the row's key) and runs `but diff <id> --json`; the diff replaces the view under the top bar until Esc, Backspace, `q`, **← Back** or a tab, and closes itself when a refresh removes that row. Action keys do nothing there (the cursor they act on is hidden); a palette action returns to the list first. `r` reloads the patch and the workspace | host |
| `but status/diff/show/oplog` in a shell | `[[lenses]]`. JSON output is parsed when the command was run with `--json`. Otherwise `parse.luau` reads the human text (your call, lenses only). A `spawn` filter gives new shells `BUT_THEME=dark` and `BUT_PAGER=cat` unless the spawn spec already carries them (the daemon's own environment is not what shells receive, so it is not consulted). Without them, `but` sends OSC 10/11 color queries and DA1, and its `less` pager turns on keypad mode, and Tern aborts any capture that does that, so no lens could ever render | host |
| Open the workspace from a git action | `tern.override("new_git_block")`: GitButler repo → workspace block, else `false` (Tern's git block) | window |
| Palette and keys | `tern.command` per action. Only ⌥⇧⌘G (open) and ⌥⇧⌘T (tui) have default `keys` (user's choice); every other command is unbound by default. Tern 0.8.3's preset holds ⌥⇧⌘B and ⌥⇧⌘S, so a plugin bind there is left out. A command opens or focuses a live block (an ended plugin pane has no surface, so a new one is opened), then sends it `{ev="action", act=…}` through `cx.session:event`, so the action runs on the block's selection with the block's confirmations. Users bind any of them as `plugin.gitbutler.<id>` in `settings.json` `keybinds` (Tern's user layer wins over plugin keys); the block's single-letter keys are fixed | window |
| `but tui` and `but gui` | Palette commands; tui also ⌥⇧⌘T. | Set up a folder (`but setup`) | Palette command "GitButler: Set up this folder". `but` 0.22.3 has no `but init`; this runs `but setup --init` in the focused pane's cwd, which creates the git repo (empty commit) only when there is none, then registers it and switches to `gitbutler/workspace`. Refuses `$HOME` and `/`, toasts "Already a GitButler workspace" when `gb.root` already matches, and on success re-probes that cwd and refreshes chrome so the segment appears at once | window |
| Raw git block opened on a GitButler repo | `git.*` are view chords, so they can't be overridden (`tern.override` takes only command ids). `pane_created`/`focus` check `cx.session:pane(id)` for `kind = "git"`, run `gb.root(path)`, and toast a warning once per pane | window |

Workspace sizing uses `width.cells` for wrapped dock text and `width.slice` for lists centered on `state.viewport`, with room for hidden-row markers. Pointer selection changes the action cursor without setting the viewport; keyboard navigation, view changes, row rebuilds, resize and changes to the dock-derived list budget reset the anchor to the cursor. Lanes also order their cards from the anchor's lane. Lanes and graph share a detail pane that budgets content against available height, and, when narrow, reserve under the list the tallest detail of every row those views can select (`detail_reserve`). Commits that share a capped body-line count and a capped file-line count, and branches that share a capped commit count, draw the same height, so each shape is measured once; the reservation follows the workspace, not the selection. Fields and preview lines that do not fit are omitted. Styled rows clip long text instead of wrapping; the branches view budgets its commit spine in pixels. Branch, commit and committed-file rows carry the branch row's `bkey`, so anonymous segments with the same empty name retain their own labels and status. The branches file pane reads the selected lane, including stack-assigned files, and windows its files using the same viewport anchor.

Programmatic `gb.run` calls are async (`tern.process.run` with `timeout_ms`), use `-C <root>`, get empty stdin, and set `NO_COLOR=1`, `GIT_TERMINAL_PROMPT=0`. State reads and mutations pass `--json`; the `but gui` launcher is the exception because it returns no model. `but tui` instead starts an interactive shell command in the workspace root. Each block allows one mutation at a time. Every mutation shows a toast with its `but` command when it starts and another with the result (or the failure), and every other outcome the dock line reports (a refusal, a stale selection, "Already up to date", a failed read) also shows as a toast, since a palette command can run while the block is out of sight. Toasts have no warning level, so warnings show as info. Reads and `but gui` time out after 15 s, ordinary mutations after 60 s, and push, PR, land and pull after 120 s.

## JSON fields relied on

- `but status -f --json`: `uncommittedChanges[]{cliId,filePath,changeType}`, `conflictedFiles[]` (unresolved uncommitted file paths, omitted when empty), `stacks[]{cliId,assignedChanges[],branches[]{cliId,name,branchStatus,reviewId,commits[]{cliId,changeId,commitId,message,conflicted,changes[]{cliId,filePath,changeType}},upstreamCommits[]}}`, `upstreamState.behind`, `mergeBase.commitId`. Mutations pass `zz:<path>`, a full `changeId`, or `<changeId>:<path>`, not the snapshot `cliId`.
- `branchStatus`: `completelyUnpushed` means every commit is unpushed, and `nothingToPush` means 0. For `unpushedCommits*`, the segment asks `but push --dry-run --json` for `branches[]{branchName,unpushedCommits}`.
- `but push --dry-run --json` (untargeted; `but push <branch> --dry-run` reports only that branch): `branches[]{branchName,unpushedCommits,requiresForce}`. Push and PR read status first and are danger when the selected branch or any branch below it in that fresh stack (top-first) has `requiresForce`, or the field is present but not a boolean, or either read fails, or the branch is missing from status. A branch the dry-run omits has nothing to push.
- `but diff <id> --json`: `changes[]{path,status,diff{type,hunks[]{diff}}}`. The hunks are joined into unified text for `tern.ui.diff`.
- `but oplog list --json`: `[]{id,createdAt(ms),details{operation,title,body}}`.
- `but pull --check --json`: `upToDate`, `upstreamCommits.count`, `baseBranch{name,remoteName,baseSha,currentSha}`, `hasWorktreeConflicts`, `branchStatuses[]{name,status,rebasable}` (`status == "conflicted"` means pulling leaves that branch's commits conflicted; `rebasable` is nullable). Missing required fields or mistyped values stop the pull. Plan comparison includes these fields and ignores branch-record order.
- `but pull --json`: `status` (`up_to_date`, `completed` or `completed_with_conflicts`, computed from branch states only) and `conflicts[]{branch,commits[]}`. It exits 0 even when it leaves conflicts, so the result notice reads the reply and waits for the post-pull status read. `conflictedFiles` supplies actual uncommitted conflicts; an unavailable or malformed status produces a warning rather than clean success.
- `but branch list --local --empty --all --no-check --json`: `branches[]{name,commitsAhead}` (unapplied branches, including empty ones, for apply). `--no-check` skips the per-branch mergeability check the picker never shows.
- Other mutation results (`commit`, `absorb`, `undo`, …) use exit status to decide success; their JSON replies supply messages.

## Action → command

| Action | Command | Confirm |
| --- | --- | --- |
| Commit marked/selected files to a branch | `but commit -b <branch> -m <msg> [zz:<path>…]` | no for a name a fresh status read shows is not in a stack, or when that branch and every branch stacked above it are `completelyUnpushed`; a failed read does not take the no-confirm path (danger). Otherwise danger (push state re-read before deciding) |
| Move uncommitted file to branch | `but amend -t <branch> zz:<path>` (amends the branch tip) | yes; danger when that branch or one stacked above it is not `completelyUnpushed` (push state re-read before the confirm) |
| Move committed file / commit to branch | `but move <changeId> -b <branch>` (a file is `<changeId>:<path>`); a typed new name creates the branch | yes; danger when either branch, or one stacked above it, is not `completelyUnpushed` (push state re-read before the confirm). A new branch name that isn't applied is left out of the push check. Refused while an uncommitted file shares a path with the change (finding 6) |
| Reorder a commit (board "Above") | `but move <changeId> --above <changeId>` | as move, both branches checked; refused under the same path overlap |
| Squash commits / move committed file into a commit (board) | `but squash <changeId> -t <changeId> --use-target-message` (no editor opens); a file is `but squash <changeId>:<path> -t <changeId>` | yes; danger as a rewrite of both branches |
| Amend files into any commit (board "Amend") | `but amend -t <changeId> zz:<path>…` | yes; danger when the commit's branch or one stacked above it is not `completelyUnpushed` |
| Uncommit commit or committed file (board) | `but uncommit <changeId>` / `but uncommit <changeId>:<path>` | yes; danger as a rewrite |
| Discard (board toolbar or right-click) | `but discard zz:<path>…` / `but discard <changeId>` / `but discard <changeId>:<path>` / `but discard <branch>` | always danger; `but undo` restores it |
| Absorb | `but absorb [zz:<path>]`; the sheet shows `but absorb --dry-run --json` first | yes; danger when a target commit's branch, or one stacked above it, is not `completelyUnpushed` (push state re-read before the confirm). On y/Enter the dry-run is repeated; if commit targets or files differ, it aborts and shows the new plan (push state re-checked) |
| Reword commit / rename branch | `but reword <changeId or branch name> -m <text>` | danger when the commit's branch or one stacked above it is not `completelyUnpushed` (rename checks only the renamed branch; push state re-read before acting); otherwise no |
| New branch (parallel / stacked) | `but branch new <name> [-A <branch>]` | no |
| Apply / unapply | `but apply <name>` / `but unapply <name>` | unapply: yes |
| Undo / redo / restore oplog entry | `but undo` (aborts if the oplog head is no longer the confirmed entry) / `but redo` (board) / `but oplog restore <sha>` | yes |
| Push / PR / land | `but push <branch>` / `but pr new <branch> -t` / `but land <branch> --yes` | yes. Push and PR are danger (`y` only) when a fresh status plus an untargeted dry-run says the branch or one below it requires force, or either read fails or the branch is missing, and the sheet says it will force-push; otherwise Enter confirms. Land is always danger |
| Pull upstream (`f`) | `but pull --check --json`, then `but pull --json` | none when `upToDate` (notice only). Otherwise danger: it fetches and rebases every applied branch onto the target; the sheet names the new commit count, the branches that will end up conflicted, and worktree conflicts. Pressing y runs `--check` again and pulls only if the checked plan still matches; otherwise the sheet reopens with the new facts (or reports up to date). Plan validation and result reporting follow the [pull JSON contracts](#json-fields-relied-on) |

Marks are file paths, captured before an async file check. Escape cancels a pending action read (the shared read drops its callback) as well as clearing marks. If a marked path is no longer an uncommitted change, the action stops and those marks are cleared; it does not commit every change. Targeted file actions refuse names containing `:` because but 0.22 interprets them as selector separators and may target another file or hunk. Polling pauses while a sheet is open so a refresh cannot retarget it. An anonymous stack still has only a snapshot CLI id; unapply re-reads status and aborts if that id now labels different commits. Undo re-reads the oplog head and aborts if it moved, because restoring that snapshot would also revert later operations. Oplog restore runs `but oplog restore` on the sha the sheet confirmed. Confirm and pick sheets take only unmodified keys (no shift, ctrl, alt, or meta) and never a paste. A prompt still accepts paste and shift+enter; other ctrl, alt, and meta chords are ignored. Escape cancels every sheet, and so does its Cancel button (a pick list can hold keyboard focus and keep Escape from reaching the block). A plain `q` cancels every sheet but a prompt, where it is text; it is checked after the modifier and paste guard, so a pasted "q" or Shift/Ctrl+Q never cancels. Confirm commands use POSIX single quotes around any argument that is not a plain token, so the line is paste-safe.

## Open questions / findings

1. **There is no CLI assignment in but 0.22.3.** `but rub` is retired, `move`/`squash` reject uncommitted sources ("Cannot pass uncommitted file or hunk as source"), and the TUI has no assign step either. The block shows `assignedChanges` (set by the GUI) read-only. `m` on an uncommitted file amends it into the chosen branch's tip, or commits it there when the branch is empty. `m` on a commit or committed file runs `but move`.
2. **Lenses vs JSON-only:** decided. Lenses parse human text and use JSON when `--json` was typed. Human status output carries push state only as color, so plain `but status` shows no pushed/unpushed badge. `but status --json` does. The status lens treats a dated `(sha …)` commit line as a two-line verbose header only when the command carried `-v`/`--verbose` (including grouped flags like `-fv`); compact subjects are free text.
3. **Remote hosts:** the status segment runs `but` on the desktop. Panes on a remote host get no segment, but the block still works, since it runs where the panes run.
4. **Unpushed counts for partially pushed branches** come from `push --dry-run`. If it omits a branch, the segment shows `N+`.
5. **`BUT_THEME=dark`** is a fixed default. On a light theme, export `BUT_THEME=light` in your shell rc. The rc runs after the spawn env, so it wins.
6. **A failed `but move` loses work in but 0.22.3.** When `move` fails with "Uncommitted files would be overwritten by checkout", it still drops the moved commit from its branch, deletes the dependent uncommitted change, and writes no oplog entry, so `but undo` is blocked by index conflicts. Reproduced with the bare CLI (`but move <changeId> -b <new branch>` while an uncommitted edit depended on that commit). Recovery: `but resolve <path>`, then `but oplog restore <snapshot before the move>`. The block refuses a move or reorder while an uncommitted file shares a path with the moved change, checked when the action starts and again on a fresh status read just before the move runs, since an edit can land while the confirm is open. Status JSON has no dependency data, so path overlap is the check.
